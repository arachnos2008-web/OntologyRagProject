All three answer the exact same question — "which stored vectors are closest to my query?" — they just trade off speed, accuracy, and memory differently. Accuracy is measured as recall@k: of the true k nearest records (what Flat returns), how many did the faster index also return? Recall@5 = 0.6 means it found 3 of the 5 true neighbours.

Flat Index

Exhaustive search — compare the query to every single vector.

k

k — number of results to return (the "k" in k-Nearest Neighbors). The only knob here: there's no approximation to tune.Example: k = 5 returns the 5 closest records.

Verdict: 100% accurate, by definition. Cost grows linearly with dataset size — fine for thousands of vectors, too slow for billions.

IVF-Flat

Cluster first, then only search the nearest few clusters.

IVF-Flat = Inverted File index with Flat storage. "Inverted file" is the library term for a lookup from a label (here, a cluster) to the items filed under it. "Flat" means that inside a chosen cluster the records are compared exactly, one by one, as in the Flat index.

nlistnprobek

nlist — number of lists (a "list" is one cluster). How many clusters the data is split into when the index is built.Example: our demo has 120 records and nlist = 8, so each cluster holds about 15 records. For big data a common start is about the square root of the record count: 1 million vectors, about 1,000 clusters.

nprobe — number of probes: how many of those clusters are visited per query. The main speed/accuracy dial.Example: with nlist = 8, nprobe = 1 searches about 1/8 of the data (fast; recall@5 was 0.64 in our rehearsal). nprobe = 8 visits every cluster, so it behaves like Flat (recall 1.0).

k — number of results to return.Example: k = 5 returns the 5 closest records found.

Verdict: much faster than Flat. Risk: if the true nearest neighbor's cluster isn't one of the nprobe clusters searched, it's simply missed — no error, just a quiet wrong answer.

HNSW

A layered graph of shortcuts — jump far on top, fine-tune at the bottom.

HNSW = Hierarchical Navigable Small World. Small world: any point can reach any other in a few hops, like "six degrees of separation". Navigable: you can find the way by always stepping to the neighbour closest to your target. Hierarchical: several layers, sparse at the top (long jumps) and dense at the bottom (fine steps).

MefConstructionefSearch (ef)k

M — maximum number of connections (links) each point keeps to its neighbours. Higher M = denser graph, more memory.Example: M = 16 (our demo) lets each point link to up to 16 neighbours. M = 4 gives a thin graph: small, but it can miss. M = 48 gives a dense one: accurate, but it uses more memory.

efConstruction — exploration factor during construction (ef_construction): when a point is added, how many candidate neighbours are examined before its M links are chosen. Higher = better graph, slower build (a one-time cost).Example: efConstruction = 200 (our demo) builds a better graph than 20, at the price of a slower build. You pay it once.

efSearch (ef) — exploration factor during search: the size of the shortlist of candidates kept while walking the graph for one query. It must be at least k. The main speed/accuracy dial, same role as nprobe above.Example: with k = 5, ef = 10 keeps a shortlist of 10 (fast, may miss one). ef = 100 keeps 100 (slower, nearly exact). Our demo uses ef = 50.

k — number of results to return.Example: k = 5 returns the 5 closest records found.

Verdict: fast and accurate for most real workloads — the default choice in most production vector databases. Costs more memory than IVF because it stores the graph's edges.
